# Framehouse Studio

An independent creative studio for the 8x assignment. Clerk workspaces contain persistent projects and FLUX.1 schnell image generations. Users can remix a project image or private upload with FLUX.2 klein 4B, compare and shortlist results, assemble a captioned storyboard, export a PNG contact sheet, and explicitly publish a read-only story link. Video, canvas editing, and a model catalogue are outside this scope.

## Local setup

Use Node 24 and PostgreSQL 17 or newer. Create a Clerk application with Organizations enabled. Copy `.env.example` to `.env.local` and replace the placeholders. Keep `.env.local` private. Set `DATABASE_URL` to a local database, then run:

```sh
npm ci
npm run db:migrate
npm run dev
```

For integration tests, set `TEST_DATABASE_URL` to a separate disposable database. Tests truncate the project and generation tables through cascading resets. Provider tests use a fake HTTP response and spend no inference.

```sh
npm run lint
npm run typecheck
npm run test:db
npm run build
```

## Deployment

The Railway project uses one web service and PostgreSQL. Set `DATABASE_URL` on the web service to the Postgres service's private connection reference. Set Clerk's publishable and secret keys as service variables, along with the Clerk route variables from `.env.example`. Set `APP_ORIGIN` to the exact public origin, such as `https://studio.example.com`, so mutation checks work behind Railway's proxy. `railway.json` builds the app, runs committed migrations before deployment, starts Next.js on Railway's port, and probes `/api/health`. `railpack.json` installs a runtime font so exported contact sheets contain legible text. The readiness probe requires the application tables to exist. Connect the `main` branch through Railway's GitHub integration and enable Wait for CI if the GitHub App becomes available. Until then, check the matching GitHub Actions run and deploy that commit manually with Railway CLI.

The GitHub workflow runs lint, typecheck, Postgres integration tests, and the production build on pull requests and pushes to `main`. It uses an isolated test database and needs no Clerk secret.

## Image generation

Set `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` only in the Railway web service environment or ignored local `.env.local`. The token needs scoped Workers AI REST permissions. Use a Workers Free account; this app does not enable paid inference. Without both variables, the composer reports that generation is being configured and the mutation route returns 503. Before enabling the integration, run `railway run --service web --environment production -- npx tsx scripts/check-flux.ts` and `railway run --service web --environment production -- npx tsx scripts/check-flux-remix.ts`. These scripts report safe result metadata or a provider error code. The remix check makes a real reference request and uses some of the free daily allowance.

One worker runs inside the web service. PostgreSQL queues generation records and stores successful JPEG bytes privately. The service allows one provider request at a time, five attempts per member and workspace per UTC day, and twenty attempts across the service per UTC day. Failed attempts count. A repeated client submission ID returns the existing record; a second active request from the same member and workspace is rejected. Interrupted work is marked failed after its lease expires, and a user can explicitly make another version. The generated bytes are served only through session and workspace checked routes.

Remixes use FLUX.2 klein 4B only when a project-owned successful result or private upload is selected. References are normalized to JPEGs smaller than 512×512 pixels before Cloudflare receives them. Uploads accept actual JPEG, PNG, or WebP content up to 5 MB, reject animation and unsafe dimensions, strip metadata, and are limited to 12 per project. Uploads and previews stay in PostgreSQL and are served through project and workspace checked routes. The submitted prompt and reference relationship persist with each result. Remixes count against the same limits as ordinary generations.

## Authorization model

Every private route derives the active organization and role from Clerk's verified server session. Project queries include the organization predicate in SQL. Members can create and edit projects; only the creator or an organization admin can archive one. Mutations require the browser origin and active workspace header to agree with the verified session. Twenty project creations per member and workspace are allowed per hour, enforced through a Postgres transaction.

Project curation stores a versioned shortlist and ordered board in PostgreSQL. It accepts only successful image IDs belonging to the active project and workspace. A stale edit returns 409 instead of replacing newer work. Preview, download, and contact-sheet export remain private and use no shared cache. Curation and export do not call Workers AI or count toward generation allowance. The three preset thumbnails are original CSS guides; they are not generated examples.

Only a project creator or workspace admin can publish or revoke its story. Publishing takes a snapshot of the title, ordered frames and captions. A 256-bit random link token grants read-only access to that snapshot for signed-out visitors; it exposes no private prompt or storage URL. Story and image routes are uncached and marked noindex. Revoking invalidates the token, including its image URLs. New board edits remain private until the owner revokes and publishes again.
